# 04 · 보안 점검과 최종 배포

**목표**: 공개해도 되는 상태인지 확인한 뒤 승인된 경우에만 Vercel에 최종 배포한다.

## 공개 전 보안 점검

다음 항목을 실제 파일과 Git 상태를 근거로 확인하고 결과를 표로 보여준다.

1. 고객 정보, 개인정보, 회사 내부 자료가 없는가?
2. 실제 데이터 대신 더미 데이터만 들어 있는가?
3. API 키, 봇 토큰, 비밀번호, Vercel 토큰이 코드와 Git 변경에 없는가?
4. `.env.local` 등 환경변수 파일이 `.gitignore`에 포함됐는가?
5. 외부 DB를 사용한다면 누구나 읽고 쓸 수 있게 열려 있지 않은가?
6. 화면과 콘솔에 시크릿이 출력되지 않는가?
7. `npm run build`가 성공하는가?
8. `npm audit --omit=dev`에 high·critical 운영 취약점이 남아 있지 않은가?

하나라도 확실하지 않으면 배포하지 않는다. 실제 데이터는 제거하고 더미 데이터로 바꾼 뒤 다시 점검한다. 화면에 비밀번호 입력창 하나를 붙이는 것으로 보안을 대신하지 않는다.

보안 판단이 어렵다면 참가자에게 아래 내용을 그대로 복사해 Claude Code에 붙여넣고 보안 체크를 한 번 부탁하게 한다.

```text
배포 전에 이 프로젝트의 보안을 점검해줘.
1. 코드와 git 기록에 비밀번호·API 키·토큰이 있는지
2. 개인정보·회사 내부 정보가 화면이나 예시 데이터에 있는지
3. .env.local이 .gitignore에 포함됐는지
4. 외부에 공개되면 위험한 관리자 기능이나 데이터 접근 권한이 있는지
비밀값의 실제 값은 절대 출력하지 말고, 문제가 있으면 위험도와 수정 방법부터 알려줘. 아직 배포하지 마.
```

결과에서 하나라도 위험하거나 확인이 필요하다고 나오면 배포하지 말고 먼저 수정한다.

## 배포 여부 확인

- 이 결과물을 공개 URL로 배포해도 되는가?
- 승인된 Vercel 계정·프로젝트와 인증 수단(CLI 로그인 또는 토큰)이 준비됐는가?

준비되지 않았거나 승인을 받지 못하면 로컬 시연으로 마친다.

## Vercel 최종 배포

- 먼저 `vercel whoami`로 CLI 로그인 여부를 확인한다. 로그인되어 있으면 기존 인증을 사용한다.
- 로그인되어 있지 않다면 `VERCEL_TOKEN`의 존재만 확인하고 실제 값은 출력하지 않는다. 토큰이 명령 기록이나 로그에 드러나지 않도록 환경변수로 전달한다.
- 배포 후 실제 URL을 열어 핵심 시나리오를 다시 확인한다.
- Vercel 프로젝트가 `sbchung-ops/mobidays-oneday-starter`에 자동 연결됐는지 확인한다. 연결됐다면 배포 URL은 유지한 채 `vercel git disconnect`로 자동 배포 연결만 해제한다.
- 인증 방식이 불분명하면 추측하지 말고 코치를 부른다.

**참가자가 직접 할 일**: 공개를 승인하고 배포 URL에서 핵심 시나리오를 확인한다.

**완료 신호**: 배포 URL이 정상 동작하거나, 배포하지 않기로 결정하고 로컬 결과를 확인한다.

**PROGRESS 기록**: 보안 점검 결과와 배포 URL 또는 `로컬 시연`을 기록하고 04 단계를 완료한다.
